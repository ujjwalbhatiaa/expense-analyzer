# expense-analyzer

A dependency-free personal-finance CLI that parses a bank-statement CSV,
categorizes spending with transparent keyword rules, and produces a monthly
summary — income vs. expenses, category breakdown, top merchants, and
month-over-month change. Optional chart export (matplotlib) for a monthly
spend bar chart and a category-breakdown pie chart.

Pairs with [csv-insights](https://github.com/ujjwalbhatiaa/csv-insights) (a
general-purpose CSV profiler) but is purpose-built for one job: turning a raw
transaction export into "where did my money actually go."

## Why keyword rules instead of an ML classifier

Real budgeting tools (Mint, YNAB) start exactly here: substring-match a
transaction description against a category's keyword list, first match wins.
It's fully explainable — you can always see *why* a transaction landed where
it did, which matters for a tool that's telling you about your own money.
Rules are plain data (a dict, optionally overridden by a JSON file via
`--rules`), not hardcoded logic, so extending coverage never touches Python.

## Design notes worth reading

| Decision | Why |
|---|---|
| Signed `amount` convention (negative = expense) | Matches how most real bank CSV exports already work; summary code never has to guess a sign. |
| Column-alias matching (`Date`/`Transaction Date`/`Posted`, `Amount` vs. `Debit`/`Credit` pairs) | Bank export formats vary a lot between institutions; the parser tries several aliases and format variants rather than assuming one schema. |
| 7 date-format attempts (ISO, US, two-digit year, `Jan 3, 2026`, etc.) | Same reason — real exports aren't consistently ISO-8601. |
| `categorize_all` returns `list[tuple[Transaction, str]]`, not `dict[Transaction, str]` | `Transaction` is a frozen dataclass but carries a `raw_row: dict` field — a dict field makes the auto-generated `__hash__` blow up at runtime despite `frozen=True`. Found this while writing the categorizer and fixed it by returning pairs instead of relying on hashability. Documented in the code, not swept under the rug. |
| Charts are optional (`--charts`), rest of the package is stdlib-only | So the core tool has zero install friction; matplotlib is only needed if you want images. |
| Synthetic sample data, generated by a seeded script (`data/generate_sample.py`), not hand-typed | Reproducible or at least understandable, includes deliberate signal (a real September tuition spike) rather than smooth uniform numbers that wouldn't exercise the month-over-month feature honestly. |

## Usage

```bash
python3 cli.py analyze data/sample_transactions.csv
python3 cli.py analyze mystatement.csv --rules my_rules.json --json out.json
python3 cli.py analyze mystatement.csv --charts reports/figures
```

`my_rules.json` overrides/extends the default categories:

```json
{
  "Pet Supplies": ["petsmart", "vet clinic"]
}
```

## Tests

```bash
pip install pytest
python3 -m pytest tests/ -v
```

**36/36 tests passing** — date-format parsing (7 formats), money-string
parsing (currency symbols, commas, accounting-style parens, signs),
CSV-shape variations (single amount column vs. debit/credit pair, alternate
header names, blank trailing rows, missing required columns), categorization
(case-insensitivity, rule-order priority, JSON rule overrides, fallback to
Uncategorized), summary math (monthly totals, category totals excluding
income, top-merchant ranking, month-over-month percent change including the
undefined-first-month case), and two end-to-end sanity checks against the
full bundled sample dataset.

## Known limitations

- Categorization is substring/keyword matching, not NLP — an unusual merchant
  name with no keyword overlap lands in "Uncategorized." The rule set covers
  the categories in the bundled sample data well (under 5% uncategorized) but
  a real user's real bank export will need `--rules` tuning for full coverage.
- No multi-currency support — amounts are treated as a single unlabeled
  currency.
- No transfer-matching between accounts (a transfer out of one account and
  into another isn't recognized as the same event, so multi-account exports
  would double-count internal transfers as both an expense and income unless
  categorized under "Transfers" and filtered out manually).
